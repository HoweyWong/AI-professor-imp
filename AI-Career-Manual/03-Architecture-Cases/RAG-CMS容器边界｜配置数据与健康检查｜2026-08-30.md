# RAG-CMS 容器边界｜配置、数据与健康检查｜2026-08-30

## 业务背景

RAG-CMS 已能在本地 Python 环境运行，但第 30 天目标要求通过 Docker 重复启动。服务同时包含应用代码、模型配置、文档与向量文件，三者生命周期和安全要求不同。

## 原有问题

- 没有可构建镜像和 Compose 入口；
- `.env`、密钥、虚拟环境和数据可能误入构建上下文；
- 容器删除可能导致文档与向量丢失；
- 容器 `running`、API 健康和模型可用容易被混为一谈；
- 主机最初没有容器运行时，静态制品无法形成运行验收。

## 核心约束

- 与项目 Python 3.9 保持一致；
- 不把 `.env`、API Key 和 `data/` 写入镜像；
- 当前文件存储必须跨容器重建保留；
- 未获授权时不调用外部模型；
- 只补单机最小闭环，不引入 Kubernetes、CI/CD 或密钥平台。

## 解决方案

```text
源码与依赖 → Dockerfile → Python 3.9 镜像
运行时模型变量 ───────────────┐
宿主机 ./data → /app/data ────┼→ Uvicorn :8000
                               └→ /health

状态分层：
容器 running → 进程已创建
容器 healthy → /health 检查通过
问答可用 → Embedding/检索/LLM 依赖另行满足
```

本机使用 Colima 提供 Docker runtime，Compose 管理构建、端口、环境变量和挂载；Buildx 负责标准镜像构建。

## 关键取舍

1. **配置运行时注入，而非烘焙进镜像。** 增加部署配置要求，换取密钥轮换和镜像复用能力。
2. **使用宿主机 Bind mount，而非镜像层保存数据。** 适合单机最小闭环且便于观察；生产环境仍需数据库、对象存储和备份策略。
3. **`/health` 保持轻量。** 外部模型故障不会把 API 进程判死，但调用方必须理解 healthy 不等于问答 ready。
4. **使用 `--wait`，不使用固定睡眠。** 等待可观察健康条件，避免机器性能变化造成偶发失败。

## 风险与限制

- 当前健康检查没有区分 liveness/readiness；
- 容器仍以默认 root 用户运行；
- Bind mount 的并发、一致性和备份能力有限；
- 基础镜像虽绑定实际 digest，但 Dockerfile 标签仍可能随下次拉取变化；
- 本地 Colima 参数不是生产容量规划；
- 哈希只能证明测试文件未变化，不能证明数据内容正确或全量数据均安全。

## 可迁移经验

- 先按生命周期划分镜像、配置和数据，再写容器文件；
- 每个“健康”结论都要写清检查了哪个能力；
- 静态校验、镜像构建、进程启动、健康检查、业务能力应分别留证据；
- 故障实验应观察真实状态迁移，而不是用固定等待时间猜测。

## 对 RAG-CMS 的启发

当前 Docker 缺口已完成实际验收。下一步不扩展编排平台；先补知识卡阶段数量。若未来部署到共享环境，再增加非 root 用户、readiness、密钥管理、数据备份和镜像安全扫描。

## 可验证行动

- `docker compose up --build -d --wait` 后 `/health` 返回 200；
- 强制重建容器后测试元数据哈希保持一致；
- 无模型配置容器的 `/health` 通过而问答返回 503；
- Python 28 项和 Java 测试在安装后继续通过。
