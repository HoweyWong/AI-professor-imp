# RAG｜分层评测与故障定位｜2026-08-06

## 所属主线

AI 应用架构

## 核心结论

RAG 质量不能只看最终答案，应拆成检索召回、答案要点覆盖和引用忠实性三层。排障时先判断正确依据是否进入 Top-K：未召回向前检查切分、Embedding 和检索；已召回则向后检查上下文、Prompt、生成和引用映射。

## 问题背景

最终答案可能偶然正确，也可能主体正确但遗漏要点或附带无依据推断。若只记录“答对/答错”，无法定位问题发生在检索侧还是生成侧，也无法可靠比较参数变化。

## 输入、处理与输出

```text
固定语料 + 问题 + 相关 Chunk + 期望要点
→ Top-K 检索 → 回答生成 → 主张与引用核对
→ Recall@K + 要点覆盖 + 引用忠实性
```

## 关键机制

### 检索 Recall@K

```text
Recall@K = Top-K 中命中的相关 Chunk 数 / 该题相关 Chunk 总数
```

它回答“人工标注的相关证据有多少进入前 K”，不回答模型是否正确使用了证据。

### 答案要点覆盖

把每题期望答案拆成可观察要点，分别判断覆盖、遗漏或错误。正确 Chunk 已召回但漏要点时，问题通常在上下文组织、Prompt 或生成模型。

### 引用忠实性

逐项检查回答中的事实主张是否被对应引用支持。答案主体正确但增加原文没有的条件关系，仍属于忠实性失败。

## 项目中的实际数据链路

```text
evals/week-02-cases.json
→ 10 个 question 与 relevant_chunk_indexes
→ embed_texts 批量生成查询向量
→ search_vectors 返回 chunk_index 排序
→ recall_at_k / mean_recall_at_k
→ 逐题结果与宏平均结果
```

回答与引用评分仍保留人工判定，避免过早引入不透明的 LLM-as-a-Judge。

## 适用条件

- 有固定语料、固定问题和人工 Ground Truth；
- 检索结果能回溯到稳定的文档或 Chunk 标识；
- 参数或实现变化前后使用同一评测集；
- 指标用于回归对比和故障定位，而非直接代表生产质量。

## 限制与风险

- 重叠切分可能让同一事实存在于多个 Chunk，相关集合标注会影响 Recall；
- Recall 高不代表答案正确，也不代表引用忠实；
- 宏平均让每道题权重相同，未反映业务问题的重要性差异；
- 单次生成结果不能代表模型稳定性；
- 调用外部 Embedding 或生成模型前，必须确认评测语料获准发送到目标服务。

## 参数实验与结论

固定检索顺序 `[0, 2, 1]`、相关 Chunk `[1, 2]`：

- `K=1`：Recall 为 `0.0`；
- `K=2`：Recall 为 `0.5`；
- `K=3`：Recall 为 `1.0`。

结论：增加 K 能提高相关证据覆盖，但也可能增加无关上下文和 Token 成本；是否改善最终答案必须另行验证。

真实 10 题实验使用 `text-embedding-v4`：

- Mean Recall@1：`0.8333`；
- Mean Recall@3：`0.9167`；
- 第 7 题从 `0.5` 提升到 `1.0`；
- 第 3、8 题暴露重叠证据导致集合 Recall 低估可回答性的标注边界。

## 一个失败案例

第 5 题的核心流程回答正确，但模型额外生成了原文不支持的条件关系。正确 Chunk 已召回，因此继续增大 Top-K 不是首要修复方向；应检查 Prompt 对“不得推断”和逐项引用的约束。

另一个工程失败是：首次真实 Recall 实验尝试向外部 Embedding 服务发送含发布规则的问题时，因缺少该数据向具体目标服务出境的明确授权而被阻止。用户明确批准后才执行成功，说明评测自动化也必须保留数据治理边界。

## 与 Java / Spring 的对照

- 结构化 JSON 类似参数化测试 fixture；
- Recall 纯函数类似无 Spring 容器依赖的 Service/工具类单元测试；
- 文件与真实检索接入属于集成测试；
- HTTP 行为才需要 Controller 层测试；
- 类比限制是 RAG Ground Truth 和生成评分需要人工判断，不能全部用字符串断言。

## 对当前项目的启发

先自动化确定性较强的检索层，再逐步结构化回答与引用评分。每次优化只改变一个主要变量，并保留相同评测集和参数记录。
