## 5. 第四步：首次构建并启动算法服务

### 确认点 B

执行下面的命令会构建镜像并创建算法服务容器。执行前确认：

- 目标 JAR 已到位且哈希一致。
- Nacos `dev-major` 命名空间已经存在 `cms-algorithm-dev.yml`。
- 配置中的数据库、Redis、日志目录等开发环境参数已经准备好。
- Compose 中算法服务端口没有与现有容器冲突。

确认后执行：

```bash
cd /home/cms/docker-business
sudo ./deploy.sh cms_algorithm
```

首次部署不要预先执行 `docker stop`、`docker rm` 或 `docker rmi`，因为当前没有算法容器和旧镜像需要清理。

### 5.1 查看容器状态

```bash
sudo docker ps -a \
  --format 'table {{.Names}}\t{{.Image}}\t{{.Status}}\t{{.Ports}}' \
  | grep -Ei 'NAMES|algorithm'
```

根据输出确定真实容器名。以下示例假设容器名为 `cms_algorithm`；如果实际名称不同，后续全部替换为真实名称。

```bash
ALGORITHM_CONTAINER=cms_algorithm
sudo docker logs --tail=500 "$ALGORITHM_CONTAINER"
```

需要持续观察时：

```bash
sudo docker logs -f "$ALGORITHM_CONTAINER"
```

按 `Ctrl+C` 退出日志查看，不会停止容器。

### 5.2 后端成功标准

- 容器状态为 `Up`，没有持续 `Restarting`。
- 日志出现 Spring Boot / CMS 工程启动成功信息。
- 没有 Nacos、数据库、Redis、端口、Mapper 或 Bean 初始化异常。
- Nacos `dev-major` 服务列表出现健康的 `cms-algorithm` 实例。

后端未通过前不要发布前端。

## 6. 第五步：前端发布前检查

下面分两种上传形式，只选择实际匹配的一种。

### 6.1 上传的是 `dist` 目录

```bash
UPLOAD_DIST=/tmp/projectIn-0825-deploy/dist
test -f "$UPLOAD_DIST/index.html" || { echo 'ERROR: index.html 不存在'; exit 1; }
test -d "$UPLOAD_DIST/static" || { echo 'ERROR: static 目录不存在'; exit 1; }
find "$UPLOAD_DIST" -maxdepth 2 -type f | head -50
du -sh "$UPLOAD_DIST"
```

### 6.2 上传的是 `.tar.gz` 压缩包

假设文件名为 `cms-vue3-dist.tar.gz`：

```bash
cd /tmp/projectIn-0825-deploy
tar -tzf cms-vue3-dist.tar.gz | head -50

mkdir "dist-extract-$RELEASE_ID"
tar -xzf cms-vue3-dist.tar.gz -C "dist-extract-$RELEASE_ID"
find "dist-extract-$RELEASE_ID" -maxdepth 3 -type f | head -50
```

解压后必须找到 `index.html` 和 `static`。根据实际结构设置：

```bash
# 压缩包内直接是 index.html/static 时：
UPLOAD_DIST="/tmp/projectIn-0825-deploy/dist-extract-$RELEASE_ID"

# 压缩包内是 dist/index.html 时，改为：
# UPLOAD_DIST="/tmp/projectIn-0825-deploy/dist-extract-$RELEASE_ID/dist"

test -f "$UPLOAD_DIST/index.html" || { echo 'ERROR: index.html 不存在'; exit 1; }
test -d "$UPLOAD_DIST/static" || { echo 'ERROR: static 目录不存在'; exit 1; }
```

## 7. 第六步：备份并替换前端

### 确认点 C

以下步骤会停止 Nginx、备份当前 `dist` 并切换新前端。执行前确认：

- 后端算法服务已经健康。
- `UPLOAD_DIST` 指向新包中真正包含 `index.html` 的目录。
- `/home/cms/docker/nginx/html/dist` 是当前线上前端目录。
- 磁盘空间足够保留旧版本。

### 7.1 停止 Nginx

```bash
sudo docker stop my-nginx
sudo docker ps -a \
  --format 'table {{.Names}}\t{{.Image}}\t{{.Status}}\t{{.Ports}}' \
  | grep -E 'NAMES|my-nginx'
```

### 7.2 备份旧前端

```bash
cd /home/cms/docker/nginx/html

test -d dist || { echo 'ERROR: 当前 dist 不存在'; exit 1; }
sudo mv dist "dist-old-$RELEASE_ID"

ls -alh
test -f "dist-old-$RELEASE_ID/index.html" \
  || { echo 'ERROR: 旧前端备份不完整'; exit 1; }
```

### 7.3 复制新前端

使用复制而不是移动，保留 `/tmp` 中的上传包，便于失败后重新处理：

```bash
sudo cp -a "$UPLOAD_DIST" /home/cms/docker/nginx/html/dist
sudo chown -R cms:cms /home/cms/docker/nginx/html/dist

test -f /home/cms/docker/nginx/html/dist/index.html \
  || { echo 'ERROR: 新 dist/index.html 不存在'; exit 1; }
test -d /home/cms/docker/nginx/html/dist/static \
  || { echo 'ERROR: 新 dist/static 不存在'; exit 1; }

ls -alh /home/cms/docker/nginx/html
du -sh /home/cms/docker/nginx/html/dist
```

### 7.4 启动 Nginx

由于前一步已经停止容器，这里使用 `start`：

```bash
sudo docker start my-nginx

sudo docker ps \
  --format 'table {{.Names}}\t{{.Image}}\t{{.Status}}\t{{.Ports}}' \
  | grep -E 'NAMES|my-nginx'

sudo docker logs --tail=200 my-nginx
```

## 8. 第七步：部署后验证

### 8.1 容器状态

```bash
sudo docker ps \
  --format 'table {{.Names}}\t{{.Image}}\t{{.Status}}\t{{.Ports}}'
```

确认 `my-nginx` 和算法服务容器均为 `Up`。

### 8.2 Nginx 本机访问

```bash
curl -I --max-time 10 http://127.0.0.1/
```

预期返回 `200`、`301` 或符合现有系统设计的正常状态，不应是连接失败或 `5xx`。

### 8.3 浏览器验证

1. 使用 `Ctrl+F5` 强制刷新 CMS 页面。
2. 登录系统。
3. 打开项目准入概览。
4. 验证项目列表、详情、人员/组织选择和本次变更功能。
5. 检查浏览器网络请求中是否出现 `404`、`502`、`503` 或权限异常。
6. 若网关拒绝访问，检查 Nacos `dev-major`：
   - `my-gateway-dev.yml` 是否存在 `cms-algorithm` 的负载均衡路由；
   - `sentinel-ruoyi-gateway` 是否存在错误的限流或熔断规则。

## 9. 前端回滚

如果新前端异常，执行：

```bash
sudo docker stop my-nginx

cd /home/cms/docker/nginx/html
sudo mv dist "dist-failed-$RELEASE_ID"
sudo mv "dist-old-$RELEASE_ID" dist

sudo docker start my-nginx
sudo docker ps | grep my-nginx
sudo docker logs --tail=200 my-nginx
```

## 10. 后端首次部署失败处理

本次没有旧算法 JAR 和旧算法容器，因此不存在后端版本回滚，只能停止失败的新容器并保留日志排查。

先确认真实容器名，再执行：

```bash
sudo docker ps -a \
  --format 'table {{.Names}}\t{{.Image}}\t{{.Status}}\t{{.Ports}}' \
  | grep -Ei 'NAMES|algorithm'

# 将下面名称替换为真实算法容器名
ALGORITHM_CONTAINER=cms_algorithm
sudo docker logs --tail=500 "$ALGORITHM_CONTAINER"
sudo docker stop "$ALGORITHM_CONTAINER"
```

未确认失败原因前不要删除容器或镜像；容器保留后仍可读取日志和构建信息。

## 11. 本次明确禁止的操作

- 不执行 `xmzr_alter.sql`，该文件包含 `DROP TABLE`。
- 不执行 `deploy.sh cms_all`，避免重建无关业务服务。
- 不执行 `deploy.sh stop` 或 `deploy.sh rm`，避免影响所有容器。
- 不根据模糊名称直接执行 `docker rm` 或 `docker rmi`。
- 不在后端启动失败时盲目重复执行审批或写操作。
- 不在旧 `dist` 尚未成功备份时覆盖前端目录。
