建立 10 个初始评测问题，运行正常、参数变化和失败三类实验，并完成首周复盘。

## 实现前预测

### 它解决什么问题

固定评测语料和问题，使切分参数、Top-K、Embedding 或回答模型变化前后可以比较，避免仅凭单次回答的主观感受判断质量。

### 输入、处理与输出

```text
固定文档 + 问题 + 期望依据
→ 切分 → Embedding → Top-K 检索 → 模型回答 → 引用回溯
→ 回答正确性 + 引用正确性 + 文档外推测记录
```

### 我的预判

- 如果没有这一步：后续优化无法证明效果是提升还是退化；
- 最重要的参数：Chunk 大小、重叠窗口、Top-K 和模型；
- 最可能的失败点：正确片段未召回，或回答正确但引用不支持结论。

## 三个实验

### 实验 1｜正常路径

- 改变或输入：直接事实题，`top_k=3`；
- 观察：正确回答固定发布窗口，引用命中 Chunk 0；
- 结论：回答和引用通过。

### 实验 2｜参数变化

- 改变或输入：同一跨段回滚题分别使用 `top_k=1` 和 `top_k=3`；
- 观察：Top-1 缺少流程片段，Top-3 召回完整依据；
- 结论：Top-K 直接影响上下文召回，跨段问题不能只看生成模型能力。

### 实验 3｜失败案例

- 改变或输入：询问文档未规定的测试环境发布时间；
- 观察：模型明确说明没有规定，并给出正确引用；
- 结论：该样例没有出现文档外推测。

## 与 Java / Spring 的对照

- 相似概念：固定语料和期望结果类似集成测试 fixture 与断言；
- 可复用的工程经验：测试数据固定、结果分层断言、回归前后使用同一基线；
- 不能直接类比的地方：RAG 输出不是完全确定值，需要分别评估检索召回、答案要点和引用忠实性，不能只做字符串相等断言。

## 我自己的复述

- 为什么需要这一步：只看最终答案可能出现偶然正确，需要检查整体链路是否完整；
- 输入和输出是什么：输入是文档、问题和检索参数，输出不仅是答案，还包括召回片段和可回溯引用；
- 参数变化有什么影响：Top-K 决定模型能看到多少候选证据；跨段答案可能需要多个 Chunk 才能完整覆盖；
- 失败时先检查哪里：先看 Top-K 是否包含正确依据，再检查上下文拼接、提示词与模型生成；如果正确依据未召回，再向前排查切分、向量化和问题表达。

### 复述纠正

如果正确 Chunk 已经召回但答案仍错误，问题通常位于生成侧或上下文组装侧，不应继续归因于 Top-K 不够。高效排查不必每次从解析重新开始，而应先在“检索结果是否正确”处分流：未召回则向前查，已召回则向后查。
