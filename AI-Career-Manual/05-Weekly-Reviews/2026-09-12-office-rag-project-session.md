# 2026-09-12｜办公文档 RAG 多文档检索与入库时段

## 今日唯一主目标

在不重启项目主线的前提下，将两份获授权的日常部署文档接入 RAG-CMS，并补齐多文档全局 Top-K 与原文件名引用，使后续价值对照能够验证“从文件集合查找”而不是“人工先选中文档”。

## 实现前预测

1. 每个文档各自 Top-K 后仍需全局排序，否则返回的不是整个集合最相关的 K 个片段；
2. 任一指定文档不存在、未切分或未向量化时，首期应整体失败，不能静默漏掉证据；
3. 多文档引用必须同时保留文档 ID、原始文件名、Chunk 和字符偏移，只有保存路径不足以供用户辨认来源。

## 数据结构与核心行为

- 新增多文档问题请求：`document_ids + question + top_k`；
- `document_ids` 限制为 1～20 个，去除前后空白并保持首次出现顺序去重；
- 查询只生成一次问题向量，对每个指定文档取候选片段，再按相似度执行全局 Top-K；
- 引用新增 `original_filename`，旧单文档路由保持可用；
- Java 引用 DTO 同步新增原文件名字段，避免跨语言后丢失来源信息。

## 真实数据链路

```text
/Users/huanghao/AiDocument 中两份授权 Markdown
→ POST /v1/documents
→ metadata.json + content.txt
→ chunk_size=800 / overlap=120
→ 13 + 8 个 chunks
→ Embedding 分批（最多 10 条）
→ text-embedding-v4 / 1024 维 vectors.json
→ POST /v1/questions（待参与者正式计时）
→ 跨文档全局 Top-K
→ 模型上下文
→ answer + 带原文件名的 citations
```

## 三个实验

### 实验 1｜正常路径

- 改变什么：上传并切分 8 个片段的命令清单；
- 观察什么：一次 Embedding 请求生成 8 个 1024 维向量；
- 结论：现有 Markdown 入库链路可直接复用，无需先扩展 PDF/Word。

### 实验 2｜多文档边界

- 改变什么：用两个文档的候选分数执行全局 Top-2，并在请求中重复文档 ID；
- 观察什么：结果按全局分数排序，重复 ID 只检索一次，引用保留实际命中文档与原文件名；
- 结论：调用方不再需要先猜答案位于哪个文档。

### 实验 3｜典型失败

- 改变什么：将 13 个 Chunk 以原 `BATCH_SIZE=100` 一次提交给当前 Embedding 服务；
- 观察什么：上游返回 HTTP 400；改为最多 10 条一批后成功生成 13 个向量；
- 结论：OpenAI 兼容接口不代表所有服务具有相同批量上限，批量大小必须作为外部服务边界验证。

## 与 Java / Spring 的对照

多文档检索类似应用服务聚合多个 Repository 查询结果后统一排序；请求 DTO 定义集合边界，Citation DTO 保持跨服务证据契约。类比限制是当前本地 JSON 文件没有数据库事务和一致性快照，多个文档在检索期间发生更新时不能保证同一版本视图。
