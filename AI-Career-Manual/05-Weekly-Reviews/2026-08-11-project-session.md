# 2026-08-11｜Week 3 第 1 次项目学习记录

## 今日唯一主目标

设计并迁移“相关 Chunk + 充分证据集合”数据结构，补充格式校验测试。

## 实现前预测

### 它解决什么问题

相关 Chunk 集合表达所有与问题有关的片段，但重叠切分可能让同一事实出现在多个 Chunk 中。只计算集合 Recall 会把“已经召回足够回答的内容”误判成证据不完整。充分证据集合单独表达能够回答问题的最小 Chunk 组合。

### 输入、处理与输出

```text
问题 + 相关 Chunk + 一组或多组充分证据 → JSON 格式与集合约束校验 → 可供后续充分证据命中指标使用的评测用例
```

### 我的预判

- 如果没有这一步：第 3、8 题会继续出现 Recall 较低但实际证据已足够的矛盾；
- 最重要的参数：`relevant_chunk_indexes`、`sufficient_evidence_sets`、Chunk 序号；
- 最可能的失败点：把“替代证据组”误写成“必须同时命中的组合”，或引用不相关的 Chunk。

## 小步实现记录

### 第 1 步｜数据结构与格式校验

- 将用例 schema 从版本 1 迁移到版本 2；
- 每题新增 `sufficient_evidence_sets` 二维数组；
- 校验二维数组及每组非空、序号是非负整数、组内和组间不重复；
- 校验每个充分证据 Chunk 都属于该题的相关 Chunk 集合。

### 第 2 步｜真实用例迁移

- 第 3 题标为 `[[0], [1]]`：Chunk 0 或 Chunk 1 任一个都包含完整的回滚 SQL 要求；
- 第 8 题标为 `[[2]]`：只有 Chunk 2 单独包含完整回滚步骤；
- 其余 8 题依据真实 Chunk 内容补充最小充分证据组。

### 第 3 步｜后续指标边界

本次只建立数据结构与加载校验，不提前实现充分证据命中指标，不改变 Embedding、Chunk 参数或回答 Prompt。

## 真实数据链路

```text
evals/week-02-cases.json
→ load_evaluation_cases
→ relevant_chunk_indexes + sufficient_evidence_sets
→ 非空、整数、去重、子集约束
→ 10 个已校验用例
→ 后续 build_retrieval_report 与充分证据命中指标
```

## 三个实验

### 实验 1｜正常路径

- 改变或输入：加载迁移后的 10 题真实 JSON；
- 观察：成功返回 10 个用例，第 3 题为 `[[0], [1]]`，第 8 题为 `[[2]]`；
- 结论：新结构能同时表达替代证据和单一充分证据。

### 实验 2｜结构变化

- 改变或输入：同一题设置两个替代证据组 `[[0], [1]]`；
- 观察：加载后二维结构保持不变；
- 结论：外层数组表达“任一组即可”，内层数组表达“一组内必须共同具备”。

### 实验 3｜失败案例

- 改变或输入：相关 Chunk 为 `[0]`，充分证据错误写成 `[[1]]`；
- 观察：加载阶段抛出“充分证据必须属于相关 Chunk 集合”；
- 结论：格式校验能阻止集合关系自相矛盾，但仍不能替代人工语义判断。

## 与 Java / Spring 的对照

- 相似概念：JSON 用例类似请求 DTO，加载校验类似 Bean Validation 加领域校验；
- 可复用的工程经验：基础格式约束和跨字段业务约束应在进入指标计算前失败；
- 不能直接类比的地方：类型与校验规则不能判断某段自然语言是否真的足以回答问题。

## 我自己的复述

- `[[0], [1]]` 表示 Chunk 0、1 任一满足即可，`[[0, 1]]` 表示 Chunk 0、1 都具备才算充分；
- 相关 Chunk 与引用支持有关，但还需进一步区分“所有相关候选内容”和“足以回答的最小证据组合”；
- `[[1, 3]]` 表示 Chunk 1、3 必须同时命中才构成一组充分证据；
- 充分证据子集校验失败时，应对照 `relevant_chunk_indexes` 与 `sufficient_evidence_sets`；不能直接把缺失序号加入相关集合，必须先依据真实 Chunk 内容判断是漏标相关 Chunk，还是错标充分证据；
- 当 Chunk 4 是无关的权限说明时，应把 `[[2, 4]]` 改为 `[[2]]`，因为 Ground Truth 必须以真实内容相关性为依据；
- 第 8 题的完整步骤集中在 Chunk 2，因此其最小充分证据为 `[[2]]`。
