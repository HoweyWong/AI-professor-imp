## 实现前预测

### 它解决什么问题

把人工表格变成固定输入，并把检索质量变成可重复计算的数值；没有这一步，后续 Top-K 或检索算法变化只能靠主观比较。

### 输入、处理与输出

```text
问题 + 相关 Chunk 标注 + Top-K 检索顺序
→ 截取前 K 个结果 → 与相关集合求交 → 命中数 / 相关总数
→ 单题 Recall@K → 所有题宏平均 Recall@K
```

### 关键边界

- `k >= 1`；
- 相关 Chunk 集合不能为空；
- 宏平均时，每道题权重相同；
- Recall@K 只评价检索覆盖，不评价答案和引用。

## 三个实验

### 实验 1｜正常路径

- 改变或输入：检索 `[2, 1, 0]`、相关 `[1, 2]`、`k=2`；
- 观察：两个相关 Chunk 均命中，结果为 `1.0`；
- 结论：顺序不影响前 K 集合中的完整召回。

### 实验 2｜参数变化

- 改变或输入：固定检索 `[0, 2, 1]` 和相关 `[1, 2]`，依次令 K 为 1、2、3；
- 观察：Recall 分别为 `0.0`、`0.5`、`1.0`；
- 结论：增大 K 可以增加相关证据覆盖，同时后续也可能带入更多无关上下文。

### 实验 3｜失败案例

- 改变或输入：相关 Chunk 为空；
- 观察：函数抛出 `ValueError`，不产生无意义的除零或默认满分；
- 结论：无 Ground Truth 的问题不能参与 Recall@K 汇总，应先修复标注。

## 与 Java / Spring 的对照

- 相似概念：JSON 类似参数化测试 fixture，纯函数类似无 Spring 容器依赖的 Service/工具类单元测试；
- 可复用经验：先验证确定性核心，再接文件、网络和 API；
- 类比限制：相关 Chunk 是人工标注，重叠切分可能产生多个包含相同事实的相关片段，指标仍依赖标注质量。

## 理解检查与纠正

- 多相关 Chunk 只召回一半时，用户正确判断 Recall 为 `0.5`；
- 若唯一正确 Chunk 排第 3，则 `Recall@1=0`、`Recall@3=1`，说明 K 的截断位置直接影响召回；
- 用户正确判断当前纯函数适合单元测试；只有进入功能对接和 HTTP 接口层面后，才需要 Controller 层测试；
- 补充边界：接入真实检索文件时可增加集成测试，但仍不必为了测试 Recall 公式启动 FastAPI。
