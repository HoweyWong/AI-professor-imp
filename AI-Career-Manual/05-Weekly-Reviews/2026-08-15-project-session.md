# 2026-08-15｜Week 3 第 3 次项目学习记录

## 今日唯一主目标

结构化答案要点覆盖与引用忠实性人工评分，并汇总到本地四层评测报告。

## 实现前预测

### 它解决什么问题

检索到充分证据后，回答仍可能遗漏要点或产生无依据主张。若人工结论只保存在 Markdown 表格里，程序无法检查缺项，也无法与检索指标稳定汇总。

### 输入、处理与输出

```text
10 题期望要点 + 人工覆盖标记 + 引用忠实性 + Top-K 结果
→ 完整性与跨字段校验 → 覆盖率计算 → 四层报告
```

### 我的预判

- 如果没有这一步：检索、生成和引用问题仍分散在不同记录中，无法形成可重复基线；
- 最重要的字段：`case_id`、`covered_point_indexes`、`citation_faithful`、`unsupported_claims`；
- 最可能的失败点：漏评用例、要点序号越界、把要点完整误当成引用忠实。

## 小步实现记录

### 第 1 步｜人工评分数据结构

新增 `week-03-manual-scores.json`，把 10 题基线的已覆盖要点、引用忠实性、无依据主张和备注结构化。覆盖率由要点序号计算，不手填小数。

### 第 2 步｜校验与纯函数

- `load_manual_scores` 校验 10 题一一对应、要点序号范围、布尔字段、备注和跨字段矛盾；
- `answer_point_coverage` 计算单题要点覆盖率；
- 缺少任意一题评分时明确报错，不静默跳过。

### 第 3 步｜四层报告

`build_four_layer_report` 在 Recall 和充分证据命中之外，加入人工答案要点覆盖、引用忠实性与两项宏平均。CLI 仅在显式传入 `--manual-scores` 时合并，避免旧人工评分误配新运行。

## 真实数据链路

```text
week-02-cases.json + week-03-manual-scores.json
→ load_evaluation_cases + load_manual_scores
→ Week 2 真实 Top-3 顺序
→ build_four_layer_report
→ week-03-four-layer-baseline.md
```

## 三个实验

### 实验 1｜正常路径

- 输入：完整 10 题标注和真实 Top-3 顺序；
- 观察：Recall 0.9167、证据命中 1.0、答案覆盖 0.8833、引用忠实性 0.9；
- 结论：四层指标能在同一报告中保持各自边界。

### 实验 2｜维度差异

- 输入：第 5 题，三个期望要点全部覆盖，同时记录一个无依据主张；
- 观察：答案覆盖 1.0，引用忠实性不通过；
- 结论：完整回答仍可能不忠实，两项评分不能合并成一个“正确率”。

### 实验 3｜失败案例

- 输入：两题用例只提供一题人工评分；
- 观察：加载阶段报错“人工评分必须完整覆盖全部评测用例”；
- 结论：强制完整评分能防止宏平均悄悄忽略未评用例。

## 与 Java / Spring 的对照

- 相似概念：人工评分 JSON 类似审核 DTO，加载校验类似 Bean Validation 加领域约束，四层报告类似聚合 Service；
- 可复用的工程经验：存原始判断，派生比例由代码计算，并让不同运行的输入显式绑定；
- 不能直接类比的地方：规则只能验证结构，不能证明人工对自然语言主张的判断正确。

## 我自己的复述

- 保存要点序号保留了具体覆盖事实，覆盖率只是结合总要点数计算出的派生结果，因此更容易复核；
- 第 4 题覆盖两个期望要点中的一个，因此覆盖率为 0.5；
- 第 5 题三个期望要点全部覆盖，因此覆盖率为 1.0，但附加了原文不支持的条件关系，所以引用忠实性失败；
- 缺失评分必须报错，因为跳过会导致运行之间分母不同，并可能隐藏恰好未评分的失败题；
- 相关 Chunk 没召回表现为 Recall 低，充分证据未进入 Top-K 表现为充分证据未命中，证据已进入但答案漏要点表现为覆盖率不足，答案正确但来源不支持主张表现为引用不忠实。
