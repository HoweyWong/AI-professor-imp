## 今日唯一主目标

在不调用 Embedding 或 LLM 服务的前提下，对冻结的开发环境文档完成首批人工查找计时，记录答案质量、依据与返工事实，为后续 RAG 对照保留可信基线。

## 实现前预测

### 它解决什么问题

接口延迟不能代表用户完成文档查找任务的时间。必须先记录人工从看到问题到提交“答案 + 可回查依据”为止的总耗时，后续才有可比较的 RAG 基线。

### 输入、处理与输出

```text
冻结 Markdown 文档 + 问题
→ 人工打开、检索、阅读并核对章节
→ 总耗时 + 答案 + 依据 + 接受度/返工
→ 价值实验逐题记录
```

### 我的预判

- 如果没有这一步：只能比较接口延迟，无法证明任务总耗时是否缩短。
- 最重要的参数：计时边界必须包含依据回查；答案质量必须以首次提交为准。
- 最可能的失败点：首次答案覆盖了部分步骤，却遗漏成功标准或异常边界。

## 三个实验

### 实验 1｜正常路径：构建顺序

- 改变或输入：`OVE-01`，公共模块修改后的系统/算法服务构建顺序。
- 观察：120 秒内查到“先 `clean install`，再打包算法服务”，并能给出避免旧 `.m2` 依赖的原因。
- 结论：问题、答案与可回查依据均完整，人工答案可接受。

### 实验 2｜失败案例：首次部署验收覆盖不全

- 改变或输入：`OVE-03`，要求同时回答部署前检查和部署后继续前端发布的证据。
- 观察：首次 90 秒答案只覆盖前置检查；提示后才补充容器 `Up`、无持续 `Restarting`、日志无关键异常及 Nacos 健康实例。
- 结论：流程题不能只列操作前条件；首次答案不完整应保留为返工事实，而不是在事后改写为成功。

### 实验 3｜正常路径：构建目录同步风险

- 改变或输入：`OVE-05`，运行容器 JAR 与宿主机构建目录不同步的后果。
- 观察：60 秒内定位到宿主机旧 JAR 会在未来镜像/容器重建时恢复旧逻辑。
- 结论：该问题适合后续与 RAG 回答及引用回查耗时作对照。

## 与 Java / Spring 的对照

- 相似概念：人工查找类似发布前基于运行手册执行 checklist；答案依据类似将操作结论关联到可审计的配置或日志证据。
- 可复用的工程经验：验收流程需同时包含前置条件、执行动作和成功判据；首次提交与返工要分别记录。
- 不能直接类比的地方：RAG 会生成自然语言并附检索引用，可能出现“回答看似完整但引用不支持”的问题；传统静态 checklist 通常没有生成式偏差。

## 我自己的复述

- 为什么需要这一步：先记录总任务耗时和质量，才不会把接口延迟误当成业务价值。
- 输入和输出是什么：输入是冻结文档和问题；输出是人工答案、依据、总耗时、接受度和返工事实。
- 参数变化有什么影响：若不把引用回查计入耗时，RAG 可能被错误地评价为更快；题目同时要求“前置条件 + 成功判据”时，遗漏一侧会降低答案可接受度。
- 失败时先检查哪里：先回到首次答案是否覆盖题目全部条件，再检查记录的章节依据是否能直接支持答案。
